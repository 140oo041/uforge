# micro_arch_IDE2 — Microarchitecture IDE, rebuilt from scratch

Design a CPU, accelerator or SoC as a graph of connected blocks, write the real
cycle-accurate C++ behind each block, **run it on a real engine**, and see — on
the canvas — where and when it does the wrong thing. Ground-up rebuild to the
contracts in `../micro_arch_IDE` (`DESIGN_PLAN.md` v3, `COMMIT_RECORD_SCHEMA.md`,
`ENGINE_FIXES.md`), with every documented seam defect fixed by construction.

It ships as **two hosts over one canvas**: a VS Code extension, and a standalone
desktop app for people who do not want an editor around it.

```
micro_arch_ide2/
├─ engine/               self-contained C++17 engine (Component/Event/Link/Scheduler/Registry/trace)
├─ packages/
│  ├─ contracts/         @iss/contracts — the read-model, write-model and host⇄view protocol
│  ├─ host/              @iss/host      — parse, write, build, run, read traces (no editor API)
│  └─ canvas/            @iss/canvas    — the schematic (React); mount it with a transport
├─ ide/                  the VS Code extension: activation, trees, webview
├─ app/                  the standalone desktop app (Electron)
├─ sample/               a 6-block design project GENERATED by the writer itself
└─ robot_soc/            an SoC demo exercising rule-based address routing
```

The split is what makes two hosts possible: `@iss/canvas` contains no editor
API and no IPC, only a `HostTransport` it is handed. The extension satisfies it
with `acquireVsCodeApi()`; the desktop app satisfies it with an Electron preload
bridge. Neither host has a private copy of the canvas, so a fix lands in both.

**Writing the C++ yourself?** [`CPP_API.md`](CPP_API.md) is the reference: the
engine API (Component / Event / Link / Registry / Scheduler / Router), the
marker contract that decides which lines the canvas may rewrite, and the exact
C++ forms the parser reads back — so a hand-written block appears on the canvas
with its ports, messages and state instead of as an opaque box.

[`CPP_API.html`](CPP_API.html) is the same reference as a page — open it from
disk, no server and no network. It is **generated** from the Markdown by
`npm run docs`; edit `CPP_API.md` and rebuild, never the HTML by hand.

## Quick start

```bash
npm install                           # one install for every workspace

# 1. Engine (once):
cd engine && make && make test        # 29/29 engine tests

# 2a. Desktop app — no VS Code needed:
cd .. && npm run build --workspace app
npm start --workspace app               # then File ▸ Open Project… and pick sample/
npm start --workspace app -- ../sample  # …or open one straight away
# (on WSL/some Linux setups add `-- --no-sandbox`)

# 2b. VS Code extension:
npm run build --workspace ide
# open ide/ in VS Code → F5 → the Extension Development Host opens ../sample

# 3. Tests:
npm test --workspace ide              # 167 headless tests (P0 acceptance incl.)
npm test --workspace app              # 6 desktop-host tests, incl. a real compile+run

# 4. Sample end-to-end with no IDE at all:
cd sample && make && ./build/design 64   # → iss_trace.jsonl (real per-hop trace)
```

### The desktop app

Same canvas, same engine, same on-disk project format — a design opened in the
app and a design opened in the extension are the same files, and either can be
opened in the other.

- **File ▸ Open Project…** (`Ctrl+O`) picks the directory holding `src/` and
  `inc/`; recents persist across launches.
- **Design ▸ Run** (`Ctrl+R`) and **Verify** (`Ctrl+Shift+R`) compile and run the
  design for real, streaming `make` output into CONSOLE and the trace onto the
  canvas.
- **Double-clicking a block opens its `.cpp` in your real VS Code**, at the
  exact line — `code --reuse-window --goto <file>:<line>`, so it lands in the
  window you already have open. Under WSL the `code` on `PATH` is the remote
  CLI, so this reaches Windows VS Code across the boundary. **Design ▸ Open
  Project in VS Code** (`Ctrl+Shift+E`) opens the whole design as a folder.
  Detection order is `code`, `code-insiders`, `cursor`, `codium`, `code-oss`;
  `ISS_EDITOR` overrides it with an id or an absolute path. With none found the
  app falls back to the OS association *and says so* rather than appearing to
  do nothing. The ledger always states which editor is wired up.
- **Six cosmetic modes**, picked from the record bar and remembered —
  **Record** (archival paper, ledger serif, custody in stroke and ink),
  **Glass** (translucent modules over a lit field), **Blueprint** (cyanotype
  drafting sheet, line only), **Terminal** (one phosphor, scanlines, monospace
  throughout), **Floorplan** (IC layout plot — macro cells on a dark die
  field) and **Paper** (white, hairline, almost nothing). Purely costumes:
  same behaviour, same semantics, same canvas. Each is scoped to
  `[data-skin='…']` and fills one `--ui-*` token contract, so adding a seventh
  touches no component.
- **The panes are yours to arrange.** Each pane collapses (⌘B list, ⌘J dock,
  ⌃` terminal), the list pane drag-resizes, and every pane header is a drag
  handle — drop one on another and they trade slots, so the inspector can sit
  on the left and the hierarchy on the right. The order is remembered per
  window.
- With no project open, the welcome screen teaches the wire grammar (solid =
  wired, orchid = routed, dashed = derived, dotted = stub, coral = unresolved)
  before anything can refuse an edit.

Renderer processes run with `contextIsolation` on and no Node integration; the
only surface they can reach is the preload bridge, which exposes the design
protocol and nothing else.

## The Figma-style canvas

- **Hierarchical modelling.** A composite block (CPU0) contains its own inner
  graph — double-click drills in, Escape/breadcrumb drills out. In code a
  composite is a C++ namespace + directory (`src/CPU0/IF.cpp` →
  `namespace CPU0 { class IF … }`); ids are dot-paths (`CPU0.IF`) and the
  Registry wires by full path. **Duplicate** clones a composite's whole
  subtree (`CPU0` → `CPU1`) as an independent copy — instant multicore. At an
  upper level, wires between levels aggregate onto the composite node (×N
  badges); cross-boundary wires label their external endpoint.
- **One `.cpp` per block, no `.h`.** Generated blocks are single-file inline
  classes (guarded by `#pragma once`; the generated harness `#include`s them
  directly). Events stay in the shared `inc/iss_events.h`.
- **Component state variables.** Each block owns state (IF has `pc`, DE has
  the decoded instruction): add them in the inspector (name, type, optional
  init like `0x80000000`) and they become real C++ members, render on the
  canvas node, and parse back from code — hand-written members show read-only.
- **Drag blocks in** from the library palette (drop anywhere; ids auto-assigned).
- **Draw wires** by dragging from a port dot (or the ＋ handle) onto another
  block; a connect popover picks/creates the event type and latency. The C++ is
  generated on confirm — solid wire = `configureOut` in code, immediately.
- **Select** (click / shift-click / marquee), **move** (grid-snapped, undoable),
  **pan** (right-drag, space, middle-drag, or the hand tool), **zoom to cursor**
  (Ctrl+wheel), **fit**, **auto-layout**, **undo/redo** (Ctrl+Z / Ctrl+Shift+Z)
  for moves, wires, adds and deletes.
- **Generic blocks**: the palette has a plain Block template plus a custom-name
  form that creates a block with the exact class name you type.
- **Input pins are real**: one pin per inbound wire, placed exactly where the
  wire lands; unwired blocks show a single waiting pin.
- **Messages open their source**: click a message name anywhere — on a block's
  port row, a selected wire's label, the inspector, or the Messages tree — and
  the event class declaration opens in the editor.
- **✉ Messages — the packet vocabulary as a place.** An editor tab (VS Code)
  and a list-pane tab (desktop app) listing every message with its wire width,
  its payload, and who emits and consumes it. Add and delete messages here
  (delete is refused, with the users named, while anything still uses one),
  edit the payload field by field, and override the derived width. Until now a
  message could only be born by drawing a wire and typing a name into the
  connect form.
- **In-ports.** A leaf's *consumed* messages get the same treatment its
  out-ports always had — width, the senders that actually reach it (by wire,
  by fabric rule), and add/remove through `setConsumes` rather than by
  hand-editing a handler signature.
- **Copy / paste blocks** (Ctrl+C / Ctrl+V). Unlike Duplicate, paste lands in
  the level you are *looking at*: copy a stage inside `CPU0`, drill out, paste
  at the top. Whole subtrees come along, internal wires are remapped, and
  pasting a composite into itself is refused rather than attempted.
- **Hover help.** Every inspector card carries an ⓘ explaining the concept in
  a sentence — "consumes", "weighted DRR", "latency model" and the rest are
  terms of art nobody should have to guess at.
- **⚙ Spec — architecture as SPEC**: Layer 1 is a general architectural
  contract for the whole design (`iss_spec.json`) — a multicore CPU spec, a
  GPU spec, an accelerator spec. New specs start from templates (RISC-V RV32I
  CPU · GPU compute core · blank); edit name/kind/xlen/harts, arbitrary named
  state (with commit-record spaces), and the operation vocabulary (summary +
  optional semantics; RISC-V formats get encoding strips). Operations the
  xverify oracle actually grades carry ✓oracle; the rest are honestly
  "spec-only" until the oracle is regenerated. Legacy `iss_isa.json` overlays
  migrate automatically.
- **Double-click a block** → its real `.cpp` opens in a native editor column
  (code is the single source of truth; the canvas is a structured editor over
  the recognized slice).
- **▶ Run** compiles the design + generated harness against `engine/` and
  animates the **real** per-hop, per-token trace (play/step/scrub/speed in the
  dock). **✓ Verify** grades the program against the reference model and
  projects divergences onto the canvas (red pulse + clickable console entries).
- Hand-written blocks appear with dashed borders — visible, revealable, and
  protected from canvas edits.

## SV co-simulation

Every leaf has a SystemVerilog twin (`src/<path>/<Block>.sv`); the generated
marker region holds the module header + ports (one `_valid` strobe per
consumed event / out-port, one signal per event field), the body below is
hand-written and survives regeneration. Setting a block's implementation to
**SV** in the inspector makes Run execute the twin for real: the twin is
verilated (`verilator --cc`, cached by mtime under `build/verilated/<id>/`),
and a generated adapter (`build/iss_sv_adapters_gen.h`) bridges it into the
engine — `handler()` latches events onto the twin's input ports, `tick()`
drives one clock pulse per engine cycle and converts `_valid` output strobes
back into engine events (token attribution via an input FIFO). C++ and SV
blocks mix freely in one binary; `test/svcosim.test.ts` proves execution with
a twin whose behavior deliberately differs from its C++ block.

## Waveforms (VCD)

When any block runs as SV, Run records a per-block VCD (`build/waves/<id>.vcd`,
verilator `--trace`; toggle in the ⚙▾ run config, on by default) and the
bottom panel grows a **WAVES** tab: one lane per signal (bit lanes as step
edges, vectors as hex value blocks), sharing the playhead with the TRACE
transport and PIPELINE grid — VCD time `2c`/`2c+1` is the posedge/negedge of
engine cycle `c`. Click a lane to scrub.

## SV↔C++ divergence checking (opt-in)

Off by default. Enable per block (⚖ checkbox in the inspector, next to the
C++|SV toggle) or for all SV blocks at once (run-config checkbox). A checked
block's adapter also instantiates the real C++ class as a **shadow**: every
input event is replayed into it, its would-be outputs are captured off
diverted links (never delivered, never traced), and each SV emission is
compared per-token, field by field. Mismatches — value differences, SV-only
emissions, C++-only emissions — surface as `[cosim]` divergences in PROBLEMS
and flash the block red. Comparison is per-token (the C++ fires at Dispatch,
the twin at Tick), exact for in-order transaction flows.

## Router fabric (top level)

Inside a composite, point-to-point wires stay the mechanism. At the **top
level**, direct delivery between units is **not allowed** — everything
crossing two top-level components must pass through a router. Drag a
◈ Router from the palette, drag from its ＋ to a component to attach it (or
to another router to trunk them); every cross-component wire then rides the
fabric: the harness stamps the packet's final destination and redirects the
link to the source's router (`Link::routeVia` — the generated `wire()` bodies
and the parser round-trip are untouched), and routers forward hop by hop
along BFS-shortest trunk paths. A cross-component wire with no fabric route
is an error: the canvas badges it `⛔ needs router` and ▶ Run refuses (with
the offender list in the console) until the endpoints are attached.

**Bandwidth is bits, and a packet costs what it carries.** A router's
bandwidth is bits per output port per cycle (default 32 — one ordinary word,
so a design that configures nothing behaves as one packet per cycle did). A
packet's width is the sum of its declared field types, shown next to every
message in the inspector and the ✉ Messages view; an event can override it
(a compressed payload, an unnamed header, a burst that is one logical
packet). Wide packets therefore *occupy* their output port: a 512-bit fill on
a 128 b/cy port takes four cycles, while several narrow packets share one.
Weighted arbitration is bit-quantum deficit round-robin, so equal weights
split bits evenly rather than packet counts — an origin sending 4×-wide
packets gets a quarter as many of them.

Contention serializes visibly; every leg is an ordinary trace hop, so the
animation, pipeline grid and PROBLEMS need no special cases. Routed wires
carry a `⇢ via R0 → R1` badge; packets still queued at the clock stop are
reported, and the METRICS tab reports bits forwarded per port alongside
packet counts.

> Sidecars written before this change stored bandwidth in packets; they are
> migrated on load at the rate the old model implied (1 packet = one 32-bit
> word), because reinterpreting `3` as three *bits* would silently throttle
> an existing design.

**Latency models.** A router is a real component with real source:
`src/<R>.cpp` holds `class R0 : public microarch::Router` — the generated
marker region carries the ctor and the `flat` default (the constant from the
inspector), and the hand-owned tail below the markers is where you write
your own models, plain member functions returning cycles for one packet:

```cpp
microarch::Cycle congested(const microarch::Event& event) {
    return event.token % 4 == 0 ? 6 : 2;
}
```

The parser picks these up (they're listed in the router's inspector panel),
and every fabric-routed wire has a **latency model** dropdown in its wire
panel offering the functions defined on all routers of its path — the
harness binds the chosen one per route (`setRouteLatency`), evaluated per
packet at forward time. Unassigned wires use the flat constant.
